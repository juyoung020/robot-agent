# RL 교사 PPO — GPU 안에서만, 그래프 둘, BF16 (계획서 G3)

[GPU_TRAINING.md](../../../docs/map_vla/GPU_TRAINING.md) 0·1·4·6–9·11절의 G3. 환경 스텝(G1) → 지도 갱신(G2) → 관측·토큰 모으기 → 정책 표본(장치 난수) → 롤아웃 버퍼 → GAE → PPO 손실·역전파 → Adam 까지 **모두 GPU** 에서 돈다.
호스트는 바퀴마다 그래프 둘을 띄우고, 끝난 바퀴의 기록을 이벤트로 확인해 읽기만 한다.

G6(FP8): 설정 `"fp8"`(기본 0 = 예전과 비트 같음), `ppo_run --steps S`(환경 스텝 예산). 검증·속도는 `../network/README.md` G6 — FP8 은 이 모양에서 느려서 기본 끔.

## 구성
| 경로 | 언어 | 내용 |
|---|---|---|
| `src/trainer.cu`, `include/trainer.h` | C++/CUDA | 장치 메모리 배치, 롤아웃·갱신 몸통, 그래프 잡기·실행, 기록 링(매핑된 고정 호스트 메모리), 체크포인트, C ABI |
| `include/ppo_capi.h` | C | Rust 가 쓰는 ABI(`ppo_create/iterate/poll/set_stage/ckpt_*`) |
| `../network/` | CUDA/C++ | 손 BF16 GEMM, 집합, PPO 손실, Adam, CPU 참조판 |
| `../observation/`, `../reward/` | CUDA/C++ | 관측 모으기(CPU·GPU 같은 소스), 퍼텐셜 모양 잡기 |
| `tools/ppo_verify.cu` | C++/CUDA | 검증 V4–V7, 음성 대조, 처리량, 결정적 평가 |
| `driver/` | Rust | 설정(JSON) 읽기, 실행 순서, 커리큘럼(A0 → A1), 비동기 기록(CSV, 쓰기 스레드), 체크포인트 |

G1 `env/`·G2 `map/` 은 **소스를 읽기만** 해서 같이 빌드한다(API·내부 변경 없음). 하나 다른 것은 빌드 옵션 `--default-stream per-thread` 다. G1 `DeviceEnv::step`·G2 `DeviceMap::step` 은 스트림 0 에 띄우는데, 레거시 기본 스트림은 그래프로 잡을 수 없다. 이 옵션으로 빌드하면 스트림 0 이 이 스레드의 스트림이 되어 같은 그래프에 잡힌다.

## 빌드·실행
```
cmake -S training/RL/ppo -B ~/ra_ppobuild && cmake --build ~/ra_ppobuild -j
~/ra_ppobuild/ppo_verify v4 | v5 | v6 | v7          # 검증(통과 = 종료 코드 0)
~/ra_ppobuild/ppo_verify v4 --negative               # 버그 둘을 넣음: 반드시 실패해야 종료 코드 0 (v5 도 같음)
~/ra_ppobuild/ppo_verify bench 4096 64 20            # 처리량
~/ra_ppobuild/ppo_verify eval <ckpt> <stage> [iters] [N] [use_map] [goal_from_map] [p0 p1 kmin kmax]
                                                     # 결정적 정책(σ → e^-12, 학습률 0) 성공률 + 처음 완성도별 표(5.6) + 충돌 다시 보기
~/ra_ppobuild/ppo_verify v4 --g4data                 # V4/V5 를 G4 자료(지도 목표·처음 지도 섞음)로
~/ra_ppobuild/ppo_verify v6 --a2                     # A2 환경 + 안 본 곳 광선(use_map 2)으로(v4/v5 는 --g4data --a2)
~/ra_ppobuild/ppo_verify snap out.bin 4096 64 6 1 1    # 빌드 사이 비트 비교용 스냅숏(두 빌드의 파일을 cmp)
cd training/RL/ppo/driver && PPO_BUILD_DIR=~/ra_ppobuild cargo build --release   # PPO_BUILD_DIR 없으면 build.rs 가 CMake 로 빌드
./target/release/ppo_run ../../config/ppo_a0a1.json --out ~/runs/a0a1 [--minutes M] [--resume ckpt]
./target/release/ppo_run ../../config/ppo_g4.json --out ~/runs/g4          # G4: 지도 목표 + 처음 지도 커리큘럼
```
출력: `log.csv`(바퀴마다), `events.txt`(커리큘럼·체크포인트), `ckpt_*.bin`(변수·Adam·학습 상태).

## v2 관측·신경망(VLA_INPUT 1–7절, 2026-10-04) — **예전 체크포인트와 호환 안 됨**
| 무엇 | v1 | v2 |
|---|---|---|
| 칸 입력(S1) | 48 = 숫자 33 + 이름 원-핫 7 + 생김새 원-핫 7 + 1 | **304** = 숫자 33(정규화 v2) + 이름 뜻 128 + 생김새 128(얼린 표 `training/data/vla_v1`, 장치에 bf16, `observation/vec_tab.h`) + 1 |
| X0 | 288 | 304(+ 다음 경유 지점 4, use_map 2) |
| 정규화 | ±10 자르기, 시간·횟수만 줄임 | 길이 sign·ln(1 + min(|x|, 5)/0.5), 각도 /π, 시간·횟수 ln(1+x) → 자료 통계 표준화(`observation/include/tok_norm.h`) |
| 행동 | `act_dims` 앞에서부터(호스트 값, 그래프에 박힘) | 장치 값 `TrainState::act_mask` — 설정 `act_mask`(0 = act_dims), 커리큘럼 단계마다 `"act_mask"`, C ABI `ppo_set_act_mask`. 환경은 늘 팔을 풂 |
| 흔들기 | 없음 | 설정 `"aug": {on, vel_sigma, prev_drop, prev_sigma, p_erase, p_syn, p_hyper, p_wrong, p_slot_drop, p_map_off, eval_unseen}` → 장치 값 `ObsAug`. 열쇠 = (바퀴, 스텝·판)이라 롤아웃과 갱신 모으기가 같은 입력 |
- 칸 MLP 묶음 커널을 넓은 칸 입력(304)으로 넓혔다 — 아래 "v2 갱신 속도". (처음 v2 커밋은 묶음 커널이 칸 입력 ≤ 64 전용이라 따로 커널 길이었다.)
- 검증(잰 값): `ppo_verify obs [--aug] [--act8] [--a2]` — 롤아웃 끝 스텝의 X0·칸 줄·채운 칸 비트를 CPU 가 같은 관측·토큰·표·열쇠로 다시 만들어 **0 낱말 다름**(흔들기 켬, 행동 8, A2 모두), `--negative`(CPU 열쇠 틀림)는 301,224 낱말 다름(정상). V4 33/33·V5 36/36(기본, `--g4data --a2 --act8 --aug` 모두), 음성 대조 버그 1·2 실패(정상), V6 0 낱말 다름(기본, `--a2 --act8 --aug`), V7 같은 씨앗 0 / 다른 씨앗 3,055,229 다름(`--a2 --act8 --aug`).
- 처리량(`ppo_verify bench 2048 64 10`, 다른 일이 GPU 를 28 % 쓰는 중, 같은 때 번갈아): v2 9.22e5 env-step/s(rollout 34.9 + update 107.2 ms, 장치 1.28 GB) / v1 빌드 1.42e6(26.8 + 65.3 ms, 0.97 GB). 갱신 +64 % 는 칸 입력 304 의 S1 GEMM 과 묶음 커널을 못 쓰는 몫, 롤아웃 +30 % 는 경유 지점 BFS·넓은 칸 입력(나눠 재지 않음, 추정).
- 실행기 확인(학습 아님): `ppo_run` 0.4 분(N 1,024, A2 설정 + act_mask 3 + 흔들기) — 단계 넘어가기·기록·체크포인트·실행 폴더가 그대로 돈다.
- **호환**: 칸 입력·X0·관측 정규화가 바뀌어 v1 체크포인트(G3–G5, A2 교사 `t4/on_s1` 포함)는 읽을 수 없다(`ppo_load` 변수 수 불일치). 설정 파일은 그대로 돈다(새 키는 모두 기본 0 = 끔).

### v2 갱신 속도 — 잰 값, 결과 비트 그대로
**재기(nsys `--cuda-graph-trace=node`, `ppo_verify bench 2048 64 6`, v2 커밋 그대로, GPU 다른 일 없음, 바퀴당 커널 합 120.7 ms)**: 갱신의 칸 MLP 줄이 바퀴당 약 61 ms —
S1·S2 앞 gemm 17.9(K 304), 모으기 `gather_k` 16.0(칸 줄 304 × bf16 = 행마다 608 B 를 씀), dW S1 11.6, dW S2 6.2, dX S2 5.6, `pool_bwd` 2.6, `pool_fwd` 0.8.
칸 줄(미니배치당 319 MB)을 모으기가 쓰고 S1 앞·dW S1 이 다시 읽는 통행이 가장 크다. 이름·생김새 128 칸은 얼린 표의 행 그대로라 행 번호만 있으면 된다.

바꾼 것(모두 출력 원소마다 같은 값·같은 mma 차례 — 누산 순서를 바꾼 것 없음):

| 바꾼 것 | 무엇 |

## 한 바퀴 (계획서 4절 그림 그대로)
```
호스트(Rust → C ABI): cudaEventRecord · cudaGraphLaunch(rollout) · cudaEventRecord · cudaGraphLaunch(update) · cudaEventRecord
                      + 끝난 칸만 cudaEventQuery 로 확인(기다리지 않음)
rollout 그래프(노드 1,167): 지난 끝 줄 → 0 줄 복사, T = 64 번 [관측 모으기 → 칸 MLP·집합·정책·가치 앞(GEMM 10) → 표본(장치 난수)
                           → G1 env_step → G2 지도(memset + 커널 셋, 토큰을 롤아웃 버퍼 t+1 줄에 바로)] → 마지막 가치
update 그래프(노드 763):  GAE·이득 통계(K4) → 에포크 5 × 미니배치 4 [섞어 모으기(Feistel 순열, 장치 열쇠) → 앞 → 손실(K5)
                           → 뒤(dW split-K, dX⊙ELU') → 조각 합 → 노름·Adam(K9)] → 기록(매핑된 호스트 링에 직접) · 바퀴 번호 +1
```
- 반복(T, 에포크, 미니배치)은 잡을 때 펼친 고정 모양이다. 조건 노드(WHILE)는 쓰지 않았다(펼친 그래프로도 호스트 동기 0 이고 노드 수가 작음).
- 바퀴마다 바뀌는 값은 장치에만 있다: 바퀴 번호(표본 난수·섞기 열쇠), 학습률(KL 로 장치에서 조절), Adam 스텝, 이득 평균·표준편차, 기울기 노름·자르기 배율.
- 결정성: 부동소수 원자 연산 없음, 모든 합은 고정 순서. 표본 난수 = hash(씨앗, 바퀴, 스텝·행동, 판).
- G1 은 끝난 스텝의 관측을 돌려준다(새 판 첫 관측이 아님). 그래서 새 판 첫 행동은 지난 판 끝 관측으로 고른다. 시간 초과 판의 가치 잇기는 이 끝 관측의 가치를 쓴다(맞는 값). 모양 잡기는 새 판 첫 스텝에 더하지 않는다. G1 에 "지금 관측" 함수가 생기면 고칠 것.
