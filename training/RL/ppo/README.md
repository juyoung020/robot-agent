# RL 교사 PPO — GPU 안에서만, 그래프 둘, BF16 (계획서 G3)

[GPU_TRAINING.md](../../../docs/map_vla/GPU_TRAINING.md) 0·1·4·6–9·11절의 G3. 환경 스텝(G1) → 지도 갱신(G2) → 관측·토큰 모으기 → 정책 표본(장치 난수) → 롤아웃 버퍼 → GAE → PPO 손실·역전파 → Adam 까지 **모두 GPU** 에서 돈다.
호스트는 바퀴마다 그래프 둘을 띄우고, 끝난 바퀴의 기록을 이벤트로 확인해 읽기만 한다.

## 구성
| 경로 | 언어 | 내용 |
|---|---|---|
| `src/trainer.cu`, `include/trainer.h` | C++/CUDA | 장치 메모리 배치, 롤아웃·갱신 몸통, 그래프 잡기·실행, 기록 링(매핑된 고정 호스트 메모리), 체크포인트, C ABI |
| `include/ppo_capi.h` | C | Rust 가 쓰는 ABI(`ppo_create/iterate/poll/set_stage/ckpt_*`) |
| `../network/` | CUDA/C++ | 손 BF16 GEMM, 집합, PPO 손실, Adam, CPU 참조판 |
| `../observation/`, `../reward/` | CUDA/C++ | 관측 모으기(CPU·GPU 같은 소스), 퍼텐셜 모양 잡기 |
| `tools/ppo_verify.cu` | C++/CUDA | 검증 V4–V7, 음성 대조, 처리량, 결정적 평가 |
| `driver/` | Rust | 설정(JSON) 읽기, 실행 순서, 커리큘럼(A0 → A1), 비동기 기록(CSV, 쓰기 스레드), 체크포인트 |

G1 `env/`·G2 `map/` 은 **소스를 읽기만** 해서 같이 빌드한다(API·내부 변경 없음). 하나 다른 것은 빌드 옵션 `--default-stream per-thread` 다. G1 `DeviceEnv::step`·G2 `DeviceMap::step` 은 스트림 0 에 띄우는데, 레거시 기본 스트림은 그래프로 잡을 수 없다. 이 옵션으로 빌드하면 스트림 0 이 이 스레드의 스트림이 되어 같은 그래프에 잡힌다.

## 빌드·실행
```
cmake -S training/RL/ppo -B ~/ra_ppobuild && cmake --build ~/ra_ppobuild -j
~/ra_ppobuild/ppo_verify v4 | v5 | v6 | v7          # 검증(통과 = 종료 코드 0)
~/ra_ppobuild/ppo_verify v4 --negative               # 버그 둘을 넣음: 반드시 실패해야 종료 코드 0 (v5 도 같음)
~/ra_ppobuild/ppo_verify bench 4096 64 20            # 처리량
~/ra_ppobuild/ppo_verify eval <ckpt> <stage> [iters] # 결정적 정책(σ → e^-12, 학습률 0) 성공률
cd training/RL/ppo/driver && PPO_BUILD_DIR=~/ra_ppobuild cargo build --release   # PPO_BUILD_DIR 없으면 build.rs 가 CMake 로 빌드
./target/release/ppo_run ../../config/ppo_a0a1.json --out ~/runs/a0a1 [--minutes M] [--resume ckpt]
```
출력: `log.csv`(바퀴마다), `events.txt`(커리큘럼·체크포인트), `ckpt_*.bin`(변수·Adam·학습 상태).

## 한 바퀴 (계획서 4절 그림 그대로)
```
호스트(Rust → C ABI): cudaEventRecord · cudaGraphLaunch(rollout) · cudaEventRecord · cudaGraphLaunch(update) · cudaEventRecord
                      + 끝난 칸만 cudaEventQuery 로 확인(기다리지 않음)
rollout 그래프(노드 1,167): 지난 끝 줄 → 0 줄 복사, T = 64 번 [관측 모으기 → 칸 MLP·집합·정책·가치 앞(GEMM 10) → 표본(장치 난수)
                           → G1 env_step → G2 지도(memset + 커널 셋, 토큰을 롤아웃 버퍼 t+1 줄에 바로)] → 마지막 가치
update 그래프(노드 763):  GAE·이득 통계(K4) → 에포크 5 × 미니배치 4 [섞어 모으기(Feistel 순열, 장치 열쇠) → 앞 → 손실(K5)
                           → 뒤(dW split-K, dX⊙ELU') → 조각 합 → 노름·Adam(K9)] → 기록(매핑된 호스트 링에 직접) · 바퀴 번호 +1
```
- 반복(T, 에포크, 미니배치)은 잡을 때 펼친 고정 모양이다. 조건 노드(WHILE)는 쓰지 않았다(펼친 그래프로도 호스트 동기 0 이고 노드 수가 작음).
- 바퀴마다 바뀌는 값은 장치에만 있다: 바퀴 번호(표본 난수·섞기 열쇠), 학습률(KL 로 장치에서 조절), Adam 스텝, 이득 평균·표준편차, 기울기 노름·자르기 배율.
- 결정성: 부동소수 원자 연산 없음, 모든 합은 고정 순서. 표본 난수 = hash(씨앗, 바퀴, 스텝·행동, 판).
- G1 은 끝난 스텝의 관측을 돌려준다(새 판 첫 관측이 아님). 그래서 새 판 첫 행동은 지난 판 끝 관측으로 고른다. 시간 초과 판의 가치 잇기는 이 끝 관측의 가치를 쓴다(맞는 값). 모양 잡기는 새 판 첫 스텝에 더하지 않는다. G1 에 "지금 관측" 함수가 생기면 고칠 것.

## 검증 (9절) — 잰 값, RTX 5070 Ti, CUDA 12.8

## 호스트 동기 (10.3 의 7) — nsys 2025.6.3, Rust 실행기 그대로
`nsys profile --trace=cuda` 로 `ppo_run` 30 초(194 바퀴). 첫 `cudaGraphLaunch` 부터 마지막까지(29.93 s) 나온 CUDA API 는 셋뿐이다.

| API | 횟수 | 바퀴당 |
|---|---|---|
| `cudaGraphLaunch` | 388 | 2 |
| `cudaEventRecord` | 580 | 3 |
| `cudaEventQuery` (기다리지 않는 확인) | 85,374 | 약 440 (Rust 가 0.3 ms 마다 확인) |
| `cudaStreamSynchronize`·`cudaDeviceSynchronize`·`cudaEventSynchronize`·`cudaMemcpy*` | 0 | **0** |

- 동기는 시작(할당·초기화·그래프 잡기, `cudaDeviceSynchronize` 2 번)과 커리큘럼 단계 바꾸기(환경·지도 새로 만들고 rollout 그래프 다시 잡기, 학습 중 1 번)에만 있다.
- 체크포인트는 `cudaMemcpyAsync` 4 개 + 이벤트(고정 호스트 버퍼) 이고 Rust 쓰기 스레드가 파일로 쓴다(기다리지 않음).

- 계획서의 "C0(전체 지도)" 시작 상태는 G2 에 아직 없다(map/README "남은 일": 커리큘럼 처음 지도). 그래서 지도 토큰은 빈 지도에서 자란다. A0/A1 의 과제 물체(컵)는 G1 관측의 참값이라 교사는 처음부터 목표를 안다(5.4 의 교사 특권). 지도 토큰은 첫 keyframe 들에서 컵을 확정한다(로그 `map_task` A0 0.96–0.98, A1 0.6–0.8).
- 처음 결정적 평가에서 체크포인트의 학습률이 되살아나 평가 중에도 갱신이 돌았다(σ = e^-12 로 망가짐 → 바퀴가 갈수록 성공률이 0 으로). `eval_iterate`(갱신 없음)로 고친 뒤 값이 바퀴마다 고르다(위 표).

## 한계·가정
- 신경망 크기(0.37M), 정규화 상수, 하이퍼파라미터, 모양 잡기 무게는 (가정). 씨앗 하나씩만 돌렸다(9.1 의 3 씨앗 비교는 하지 않음).
- 행동은 G1 의 8 개를 내지만 approach 단계는 앞 2 개(vx, wz)만 학습하고 나머지는 0 고정(CURRICULUM 3절).
- 이름·생김새는 원-핫이다(SigLIP 표 없음).
- `map/` 은 커밋 c6b5cc5 위에 다른 작업자의 커밋 전 내부 최적화가 든 작업 트리로 빌드했다(API 같음, MapTok 같음).
