# VLA 설계 Q&A (Claude 버전)

`untitled.md`는 Gemini 대화가 여러 번 붙여넣기되어 중복이 많았습니다. 그래서 질문 7개만 추려 시간순으로 정리하고, 제가 답했을 내용으로 다시 작성했습니다. 원본은 그대로 두었습니다.

Gemini 답변 중 틀렸거나 과장된 부분은 각 답변 끝의 **정정**에 따로 적었습니다.

## Q1. 파이 0.5 신경망 크기가 어느 정도야?

전체 약 **3.3B** 파라미터입니다. PaliGemma 계열 VLM에 작은 액션 전용 트랜스포머를 붙인 구조입니다.

| 구성 | 크기 | 비고 |
|---|---|---|
| SigLIP 비전 인코더 | ~0.4B | 이미지 → 패치 토큰 |
| Gemma 언어 백본 | ~2.6B (Gemma 2B + 임베딩) | 이미지·텍스트·상태 토큰 처리 |
| Action Expert | ~0.3B | 연속 액션 생성 (Gemma 계열 소형 트랜스포머) |

OpenVLA(7B)의 절반 이하입니다. 다만 "단일 GPU에서 추론이 원활하다"와 "단일 GPU에서 학습이 된다"는 별개입니다. 이 차이는 Q7에서 다룹니다.

## Q2. 학습할 때 액션 출력 쪽이 그냥 MLP야?

**아닙니다.** Action Expert는 MLP 헤드가 아니라 **별도의 소형 트랜스포머(~300M)** 입니다.

- 백본과 같은 어텐션 구조를 공유하며, 백본 토큰(이미지·텍스트·상태)을 보면서 액션 토큰을 처리합니다. 두 개의 expert가 어텐션을 공유하는 MoE 비슷한 형태입니다.
- 출력은 **flow matching**으로 만듭니다. 노이즈 액션 청크에서 시작해 몇 스텝(보통 10스텝)에 걸쳐 속도장(vector field)을 적분합니다. 학습 손실은 속도장에 대한 MSE입니다.
- 한 번에 액션 **청크(예: 50 step)** 를 출력합니다.
- π0.5는 사전학습에서 FAST 같은 이산 토큰 액션도 함께 학습하고, 추론과 post-training에서는 flow matching expert를 씁니다. 또 행동 전에 서브태스크를 텍스트로 먼저 예측하는 계층 구조도 있습니다.

**정정:** Gemini의 "머리=이산 토큰 / 소뇌=flow matching"이라는 비유는 대체로 맞습니다. 하지만 "단순 MLP가 아니다"를 설명하면서 Action Expert가 트랜스포머라는 핵심은 빠뜨렸습니다.

## Q3. 뎁스값과 현재 pose를 state로 받게 하고 싶어. 4090 한 대라 LoRA로 어떻게 시작해?

### Pose
- π0.5는 이미 **state를 이산화(256 bin)해서 프롬프트 텍스트 토큰으로** 넣는 방식입니다. 그래서 pose를 텍스트로 넣는 것은 새로운 시도가 아니라 **기본 경로**입니다. state 차원에 pose를 넣고 정규화만 맞추면 됩니다.
- 구조 변경 없이 쓸 수 있으니 **먼저 이 방식으로 시작**하세요.

### 뎁스
- 포인트클라우드는 그대로 못 넣습니다. **카메라 시점으로 투영한 depth 이미지** 또는 **BEV 이미지**로 바꿉니다.
- openpi는 이미지 슬롯이 3개(base, left wrist, right wrist)입니다. 비는 슬롯에 depth를 넣으면 **구조 수정 없이** 들어갑니다.
- 1채널이면 3채널로 복제하거나 colormap(Turbo 등)을 적용해 SigLIP에 넣습니다.
- SigLIP은 depth로 사전학습된 모델이 아닙니다. 완전히 동결하면 기하 정보가 약할 수 있습니다. 성능이 부족하면 **비전 쪽 LoRA를 일부 열거나** depth 전용 작은 어댑터를 추가하세요.

### 학습 세팅
- Gemma 백본과 Action Expert에 LoRA를 적용하고, SigLIP은 일단 동결합니다.
- 4090(24GB)에서 openpi LoRA 파인튜닝은 가능한 범위입니다. 메모리가 빠듯하면 batch를 줄이고 gradient checkpointing을 켜세요.

**정정:**
- Gemini가 말한 `policy_postprocessor.json`은 LeRobot 쪽 파일입니다. openpi는 **내 데이터셋으로 계산한 norm stats**(`compute_norm_stats`)로 정규화합니다. 사전학습 통계에 맞출 필요가 없고, 내 데이터 기준으로 다시 계산해야 합니다.
- Gemini가 말한 batch size "12 / 48배수"는 글자가 깨진 값입니다. 4090이라면 실제로는 배치 1~4 + grad accumulation입니다.
- openpi 기본 경로는 bitsandbytes 4-bit QLoRA가 아니라 JAX/PyTorch의 bf16 LoRA입니다. 4-bit는 직접 붙여야 합니다.

## Q4. 물체가 이미 세그멘테이션되어 있고, 등록된 위치에 그대로 있어. VLA가 이 지도를 읽게 하고 싶어. π0.5가 아니어도 돼.

### 입력 방식 두 가지
1. **텍스트 scene graph (추천 시작점)**
   - 객체의 `class`, `id`, **로봇 기준 상대 좌표**를 넣고, 반경 N m 안의 객체만 필터링합니다.
   - 좌표는 월드 좌표보다 **로봇 프레임 상대 좌표**가 학습에 훨씬 유리합니다. 모델이 좌표 변환을 배울 필요가 없습니다.
   - 숫자는 소수점 1~2자리로 반올림해 토큰 수를 줄이세요.
2. **객체 토큰 방식 (2단계 실험)**
   - 객체마다 `[class 임베딩 + 위치 MLP]`로 토큰 1개를 만들어 백본에 직접 넣습니다.
   - 숫자를 텍스트로 쪼개는 비효율이 없고 토큰 수도 적습니다. 대신 새 모듈을 학습해야 합니다.

### 모델 선택
- π0.5는 **이미 로봇 액션 사전학습이 되어 있다**는 점이 가장 큰 장점입니다. 데이터가 적다면 처음부터 만드는 것보다 π0.5 LoRA가 유리합니다.
- 직접 제작하려면 `VLM 백본 + 액션 헤드(ACT 또는 diffusion)` 조합이 가능합니다. 이 경우 액션 사전학습이 없으므로 **데이터가 훨씬 많이 필요합니다.**

### 학습 순서
1. (선택) 지도 텍스트 → 상황 설명 생성으로 지도 이해를 먼저 정렬합니다.
2. 행동 복제(behavior cloning)로 액션을 학습합니다.

**정정:**
- Gemini가 말한 "Qwen2.5-VL 2B"는 존재하지 않습니다. Qwen2.5-VL은 3B / 7B / 32B / 72B이고, 2B는 Qwen2-VL입니다.
- "SigLIP + Qwen"을 조합한다는 설명도 맞지 않습니다. Qwen-VL은 자체 ViT를 갖고 있습니다.
- "Qwen이 좌표 추론에 특화"라는 말은 사실이지만, 로봇 액션에 대한 사전학습이 없다는 점은 따로 고려해야 합니다.

## Q5. 리모 카메라와 매니퓰레이터 카메라 2개를 넣을 때, 지도는 RGB로 줄까, pose와 가면 안 되는 곳 값으로 줄까? (지도는 실시간 업데이트)

**카메라 2개는 그대로 이미지 입력으로 넣으세요.** π0/π0.5는 base 카메라 + wrist 카메라 구성이 기본입니다. 문제는 지도 쪽입니다.

### 추천: 수치(텍스트) 먼저, BEV 이미지는 비교 실험
| 방식 | 장점 | 단점 |
|---|---|---|
| 텍스트: pose + 객체 + 방향별 거리 | 가볍고 해석 쉬움, 디버깅 쉬움 | 복잡한 지형·좁은 통로 표현이 약함 |
| BEV 코스트맵 이미지 (저해상도) | 금지 영역의 **형상**이 그대로 표현됨 | 이미지 토큰 +256개, 학습 데이터 필요 |

- "가면 안 되는 곳"이 **점이나 방향별 거리**로 충분히 표현되면 텍스트로 가세요. 예: `front: 0.5m blocked`.
- 금지 영역이 **복잡한 형상**이면 64×64~128×128 BEV를 세 번째 이미지 슬롯에 넣는 쪽이 낫습니다.
- 결정하기 어려우면 **둘 다 만들어 비교**하세요. GT에서 뽑는 데이터라 두 입력을 만드는 비용이 거의 같습니다.

**정정:** Gemini는 "지도 RGB는 데이터가 엄청 많이 필요하니 비추"라고 단정했는데, 근거가 약합니다. 저해상도 BEV는 VRAM에 크게 부담스럽지 않습니다. 비교 실험이 필요한 문제입니다.

## Q6. 실시간으로 지도가 생기는데, 그 시퀀스를 즉석에서 보고 판단할 수 있어야 해.

### 핵심은 시퀀스를 쌓는 것이 아니라 **빠르게 다시 계획하는 것**
- 지도의 *변화 자체*를 모델이 추론해야 하는 경우는 많지 않습니다. 대부분은 **현재 지도 + 짧은 재계획 주기**로 충분합니다.
- **Receding horizon:** 청크(예: 50 step)를 예측하고 앞의 5~10 step만 실행한 뒤 새 지도로 다시 추론합니다. 장애물이 갑자기 생겨도 다음 추론에서 경로가 바뀝니다.
- 추론 지연이 문제라면 이전 청크를 이어 쓰는 **비동기 추론(예: real-time chunking)** 을 고려하세요.

### 정말 "변화"가 필요하다면
- 이전 스텝의 요약 1~2개(예: 장애물 거리 변화량)를 텍스트로 추가합니다. 프롬프트가 조금 길어질 뿐입니다.
- 단, 이 방식으로 학습하려면 데이터에 **시간 순서가 보존**되어 있어야 합니다.

## Q7. 5070 Ti 16GB에서 학습하려면 얼마나 줄여야 해? (지도 갱신은 GT로 미리 뽑아서 시퀀스 없이 병렬 처리할 거야)

### 먼저 현실 확인
- openpi 문서 기준으로 π0.5 **LoRA 파인튜닝에 약 22GB 이상**이 필요합니다. 따라서 **16GB에서는 기본 설정 그대로는 안 됩니다.** 이 수치는 문서에서 기억한 값이니 실제 환경에서 확인하세요.
- 16GB에서 시도할 수 있는 방법은 다음과 같습니다.
  1. 8-bit/4-bit 양자화 + LoRA (직접 구현 필요, 호환성 확인 필요)
  2. 이미지 해상도 축소, 이미지 수 제한 (예: 2장, 224px)
  3. gradient checkpointing, micro-batch 1 + grad accumulation, 8-bit 옵티마이저
  4. 더 작은 모델로 전환 (예: SmolVLA ~450M은 16GB에 여유 있게 들어갑니다.)
- 순서는 **작은 모델로 파이프라인을 먼저 검증**하고, 필요할 때 큰 모델로 올리는 것을 추천합니다.

### 입력 예산 (제안)
- 이미지: 224px 기준 장당 256토큰, 2~3장.
- 지도 텍스트: 100~200토큰 이내.

### GT 지도를 병렬 학습할 때 주의할 점
- 샘플이 서로 독립이라 셔플과 병렬 로딩이 자유롭고 구현이 단순해집니다. 이 결정 자체는 좋습니다.
- **가장 큰 위험은 train/deploy 불일치입니다.** 학습은 GT 지도로 하는데 배포 때는 SLAM이 만든 지도를 씁니다. 위치 오차, 누락, 오탐이 생기므로 학습 때 **지도에 노이즈·누락·오분류를 주입**하세요. 그러지 않으면 실제 로봇에서 성능이 크게 떨어집니다.
- 시퀀스를 없애면 컨텍스트가 짧아져서 메모리가 줄어드는 것은 맞습니다. 다만 어텐션이 O(N²)로 "폭발"할 만큼의 길이(1~2k 토큰)는 아니므로, 메모리 절감의 주된 이유는 토큰 수 자체가 줄기 때문입니다.

**정정:** Gemini의 "16GB에서도 충분히 학습 가능"은 너무 낙관적입니다. 3.3B 전체를 쓰려면 양자화 등 추가 작업이 필요하고, 작은 모델로 시작하는 편이 안전합니다.

## 요약: 이 순서로 시작하세요
1. **작은 데이터셋으로 파이프라인 검증** (SmolVLA 또는 openpi 소량 데이터)
2. pose는 **state 입력**, 지도는 **로봇 기준 텍스트**로 시작
3. 카메라 2장 + (선택) depth/BEV 1장
4. 학습 때 **지도 노이즈 주입**
5. 추론은 **짧은 재계획 주기**로 운용
6. 성능 병목이 확인되면 그때 객체 토큰이나 BEV 이미지를 추가
